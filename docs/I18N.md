# UI languages

The web app, the landing page and the login page are fully translated into English (default), Hindi and Telugu: no English sentence is left on screen in Hindi or Telugu (work order v2 §7). 2,243 keys in 62 namespaces, the same set in all three files.

## How it works

- `web/src/i18n/index.ts` sets up i18next with `react-i18next`. The strings live in `en.json`, `hi.json` and `te.json`, and every key exists in all three files. A missing value falls back to English.
- The language comes from `localStorage['lang']` (`en`, `hi` or `te`; anything else means English) and is set on `<html lang>`.
- The switcher at the bottom of the sidebar calls `setLanguage(lng)`, which saves the choice and re-renders at once. The landing page follows the saved choice.
- Numbers use `localeFor(lng)` (`en-IN`, `hi-IN`, `te-IN`) with Latin digits and Indian grouping in all three. The `₹` prefix and the `−` minus are the same in every language. Dates and month names shown as words (`formatDate`, `formatDateTime`, `formatMonth`, the landing charts) use `Intl` in the UI language; English keeps its own short month names ("Sep").
- Fonts: Inter, then Noto Sans Devanagari and Noto Sans Telugu (`tokens.css`, linked from the three HTML pages). Hindi uses line-height 1.55 and Telugu 1.6.
- Translated: everything the UI writes, including tooltips, aria-labels, chart titles and summaries, empty and error states, toasts, the landing page (`landing/content.ts` keeps the English defaults next to each key) and the login page.
- Engine text the API sends in English (waterfall line names and notes, leak causes, interventions and their rules, scenario notes, validation flags, Pulse actions, margin formulas, reconciliation statements, evidence reasons) is shown in the UI language by `web/src/lib/apiText.ts`: each entry is a key plus the engine's exact English sentence with `{{placeholders}}`; a sentence that matches is rebuilt from the translation with the same values, anything else is shown as sent. `tests/api-text.test.ts` runs the engine and fails when an engine sentence is no longer recognised.
- Not translated, on purpose: data values (order ids, channel and product names), CSV column names (`refund_inr`), file names, code identifiers, brand and format names (Profyn, AI, CSV, JSON, CM1–CM3, Shopify …), the contents of downloaded files, and the change-log body rendered from `docs/*.md`.
- English accessible names must stay as they are, because `scripts/ui-smoke.mjs` finds controls by them.

## Adding a key

1. In a component, write the text through `t()` with its English as the default: `const { t } = useTranslation();` then `t('screen.key', 'English text')`. Group keys by screen or component (`import.*`, `pulse.*`, `ledger.*` …). Never change an existing English string: `scripts/ui-smoke.mjs` and the jsdom tests find controls by their English names.
   - Values: `t('k', 'Totals differ by {{inr}}', { inr })`. Keep the `{{placeholder}}` names identical in hi and te.
   - Counts: plural keys `k_one` / `k_other` with `t('k', '{{count}} orders', { count })` (Hindi and Telugu need both forms too).
   - Text around a link or bold word: `<Trans i18nKey="k" defaults="Read the <1>docs</1>" components={{ 1: <a /> }} />`, so Hindi and Telugu can change the word order.
   - Tables at module level (options, tabs, labels): keep `{ labelKey: 'ns.key', label: 'English' }` and render `t(x.labelKey, x.label)`, or translate inside the function that reads the table (`lib/labels.ts` does this), never at import time.
   - Plain `.ts` modules (API client, auth): `i18n.t('k', 'English')` when the message is created.
   - Mid-sentence lower case: `lower(t(...))` from `web/src/i18n`.
2. Add the key with its English, Hindi and Telugu text to `en.json`, `hi.json` and `te.json`, in the same place in each file. The English in `en.json` must be exactly the default written in the code.
3. A new English sentence from the API engine: add it to `API_TEXTS` in `web/src/lib/apiText.ts` (key and the engine's exact English) and wrap the render site in `apiText(...)`.
4. Run `npm test`. Four tests guard the translations:
   - `tests/no-literals.test.ts` fails, listing file:line, on any English word in `web/src/**/*.tsx` JSX text, visible props (title, aria-label, placeholder, alt, label …) or string literals rendered as children that does not go through `t()`. Intentional Latin text (brands, formats, units, code identifiers) goes in `tests/i18n-literal-allowlist.json`.
   - `tests/i18n-coverage.test.ts` fails when a key used in `web/src` is missing from a language, when the three files do not have the same keys, when placeholders differ, or when a Hindi or Telugu value is still English (outside the allowlist below).
   - `tests/api-text.test.ts` checks the engine sentences (above).
   - `tests/i18n.test.tsx` checks the sidebar in all three languages and the switcher.

## Status

All 2,243 keys have Hindi and Telugu text (about 1,080 of them added in the full-translation pass: `apiText`, `pulse`, `login`, `hero`, `pricing`, `samples`, `recon`, `info`, `app`, `api` and more under the existing namespaces). A native speaker should still review them, newest first.

These stay the same in all three files on purpose: `brand` (Profyn), `lang.en`, `lang.hi` and `lang.te` (each language is named in its own script), and `status.ai` (AI).

`nav.step` (`Step {{n}}: {{label}}`) and `nav.done` make up the sidebar's accessible names. Keep the `{{n}}` and `{{label}}` placeholders when you change them.

## Glossary

Every Hindi and Telugu string uses these terms. `tests/i18n-coverage.test.ts` fails when a key used in `web/src` is missing from any language, when placeholders differ, or when a Hindi or Telugu value is still English (outside the allowlist below).

Keep in Latin script, untranslated: Profyn, AI, CSV, JSON, CM1, CM2, CM3, ₹, COD, UPI, Shopify, Meta Ads, Google Ads, Shiprocket,
Razorpay, Markdown, PDF, API, URL, SKU, GST, ID, also file names / code identifiers (e.g. decision-{{id}}.json, order_id, refund_inr).
Placeholders like {{n}}, {{count}}, {{inr}} must be copied EXACTLY (same names, same count). Keep the "·", "—", "→", "−", "=" symbols.
Formulas like "net revenue = revenue − refund": translate the words, keep the symbols.
